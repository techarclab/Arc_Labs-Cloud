# Security review (design plan §17)

Status of each control in this codebase. ✅ in place · 🟡 partly / depends on hosting · ⬜ owner action.

| Control | Status | How |
|---|---|---|
| TLS for web, API, MQTT | ✅ | Vercel + Railway HTTPS; EMQX TLS 1.2/1.3 on 8883; plain MQTT 1883 only on the private network. Internal links (api⇄emqx⇄worker) use Railway's private network. |
| Unique per-device credentials; rotation; revocation | ✅ | 256-bit random password per device, scrypt-hashed. Rotate/revoke/suspend/retire also disconnect the live session via the EMQX management API (`EMQX_API_*`); without it, the 30 s ACL cache bounds the delay. Device HTTP keys go in the `Authorization` header; `DEVICE_KEY_IN_QUERY=false` refuses keys in URLs. |
| No anonymous MQTT; topic ACLs per device | ✅ | Every client authenticated by the API hook; device may publish only its own `telemetry`/`state`/`cmd-ack` and subscribe only its own `cmd`. |
| Backend RBAC and tenant checks on every read/write | ✅ | `AccessService` resolves ownership from the DB; non-members get 404. API keys, service accounts and LMS learners carry an org/channel/device scope enforced in the same place. Tested end-to-end. |
| Database-enforced tenant isolation | ✅ | PostgreSQL row-level security on every tenant table (migration 004). Authenticated requests run as `arc_tenant`, pinned to the caller's organizations, so a query missing its organization filter returns nothing from other tenants. E2E proves both the policies and that API writes run under that role. System paths (worker, broker hooks, device key lookup, sign-in, platform admins, org creation) run as the owner by design. Gap: on a TimescaleDB hypertable (local Docker), `telemetry_measurements` has no RLS. RDS PostgreSQL (the AWS target) has no TimescaleDB, so it applies there. |
| Rate limits and payload limits | ✅ | 300 req/min per client, 10/min on login, 30/min on OAuth; per-device MQTT 5 msg/s (burst 20) and HTTP 1/s; JSON body 256 KB; MQTT packet 16 KB. |
| Input/schema validation | ✅ | zod on every API input (also generates the OpenAPI docs); telemetry schema + per-field min/max; command parameters validated against an allow-list. |
| Dependency scanning | ✅ | CI runs `npm audit --omit=dev --audit-level=high` on every push. Known: 2 moderate advisories in `js-yaml` via `@nestjs/swagger` (only parses the platform's own spec, never user input). |
| Secrets management; none in source or frontend | ✅ | Railway variables; CI fails if `.env`, device files, `railway-variables.txt`, private keys or certs are committed. The console bundle only contains the public API URL. |
| Device-side TLS | ✅ | Reference firmware verifies every server certificate against pinned public roots (`arc_roots.h`: Amazon Root CA 1/3, ISRG Root X1, GTS Root R1). It never uses `setInsecure()` (CI-enforced), and plain `http://` is refused unless explicitly allowed for local testing. Owner: confirm your API/broker chain to one of these roots (`openssl s_client`). |
| Console XSS hardening | ✅ | Content Security Policy injected at build: no inline scripts or eval; scripts only from self + Google sign-in; connect only to the API. Hosts add `frame-ancestors 'none'`, HSTS (Vercel) and Permissions-Policy. Custom boards render in `<iframe sandbox="">` with their own script-free CSP. Checked in Chromium on the seeded demo: no violations, and an injected inline script was blocked. Remaining: the session token lives in `localStorage`, so CSP is what protects it. Moving to an httpOnly cookie is planned for the AWS move, when console and API share a site. Also fixed: nginx dropped all security headers on `index.html` because a location-level `add_header` overrode them. |
| Audit: provisioning, credentials, rules, commands, exports | ✅ | `audit_logs` records device create/rotate/revoke/lifecycle, rules, alert ack/resolve, API keys, webhooks, LMS tokens, commands, firmware, settings/plan changes, read-key rotation. |
| Commands safety | ✅ | Allow-listed per channel, parameter validation, role check (engineer or admin-only types), expiry, status only "acknowledged" after the device confirms. |
| OTA authenticity/integrity | ✅ | Devices verify an ECDSA P-256 signature over the exact manifest bytes with a public key compiled into the firmware, and take url/SHA-256/size/version only from the signed manifest. They refuse other device types and downgrades, check size + SHA-256 over certificate-verified HTTPS, and roll back an image that cannot reach the cloud within 5 minutes (Arduino-ESP32 3.x bootloader rollback is on; checked on 3.3.12). The server also verifies signatures at release time. CI cross-checks the C verifier against the signing tool and compiles the sketches for ESP32 and ESP32-S3. Before this change only the server checked the signature, so a compromised cloud, broker or network path could push an image. Still open (owner): ESP32 Secure Boot v2 + flash encryption on production hardware, and keeping the signing key offline. |
| Webhook safety | ✅ | HTTPS only, private/loopback addresses refused (checked at creation and at each send), HMAC-SHA256 signature with timestamp, 10 s timeout, no redirects, bounded retries. |
| Backups and tested restore | ✅ | `infra/backup/*` with checksum + row-count verification; verified in CI. Enable Railway scheduled backups too (⬜ owner). |
| Incident response, data export/deletion | 🟡 | Runbooks in `docs/runbooks`. Data export: channel CSV/JSON feeds and the API. Deleting an organization's data on request is a manual SQL step today (document requests in the audit log). |
| Indian privacy/legal review (DPDP Act 2023) | ⬜ | Owner action before storing personal data: privacy notice, consent where needed, data-processing agreements with Railway/Vercel, breach-notification procedure. Not legal advice. |
| Penetration test | ⬜ | Recommended before the first paying customer. |
